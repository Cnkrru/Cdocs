44 篇文档 × 2 语言 × 2 版本，构建耗时从 16 秒优化到 ~1.4 秒（全量）/ ~0.85 秒（增量），19 倍提速。

## 问题

Cdocs 是一个 C++ 单文件静态站点生成器，最初的构建速度远慢于竞品：

> 44 页构建 16s，Hugo 同等量级不到 0.1s。

## 诊断

通过 `[perf]` 探针定位到三层瓶颈：

1. **插件子进程**：每次钩子调用 spawn Python 解释器，Windows 冷启动 ~0.45s/次，`on_data_query` 和 `on_config` 累计 ~4s
2. **串行渲染**：页面只在 `render_doc_pages` 内并行，标签/市场/博客/404 全部逐页串行
3. **每页多余开销**：组件 HTML 文件搜索、JSON 地图逐段解释执行、多次字符串拷贝

## 优化清单

### 查询内置化

`blog-query` 和 `tags-query` 的逻辑从 Python 插件迁移到 C++：

- 标签聚合、博客排序/分页/首页流 — 全部在 `prepare_pages` 阶段完成
- 输出格式与插件一致，向下兼容
- 消除了 `on_data_query` 钩子的全部子进程

### 渲染全面并行化

所有页面类型均使用 Hugo 式 `run_parallel` worker pool：

- `render_doc_pages`：两阶段（渲染正文 → 输出页面）
- `render_blog`：详情页两阶段 + 列表分页并行
- `render_tags`：每标签单页并行
- `render_markets`、`render_single`：直接并行
- 多 locale 并行：zh-CN 和 en 同时渲染

### 组件系统优化

- **组件 HTML 预加载**：启动时一次性扫描 `components/` 目录到内存，消除每页递归文件搜索
- **地图预编译**：JSON sections 编译为 FlatCmd 指令列表，渲染时直写 buffer 不遍历 JSON
- **输出管线融合**：`i18n_replace` + `minify_html` + `wrap_webp` + `fingerprint` 统一为 `finalize_html` 调用

### 资产复制加速

Windows 下 `robocopy`（系统批量拷贝 API）替换 `std::filesystem::copy`（逐文件拷贝）。130+ 个 KaTeX 字体、JS、CSS 的复制从 ~6s 降到 ~0.3s。

### 增量构建

- 三层签名（全局配置 / 页面源 / 资产文件）判定未变则跳过
- 不再限制 `serve -w` 模式，`Cdocs build` 始终启用增量
- 所有页面类型（文档/博客/标签/市场/404）均支持增量跳过
- 未生成页面自动清理残留 HTML

### 其他

- `on_config` 守卫：多版本构建只执行一次插件钩子
- 资产签名快检：目录 mtime 替代 130+ 文件递归 stat
- 持久插件进程：Python 解释器常驻，热调用 ~0.01s
- 死链检查重构：修复并发写盘后的文件系统缓存误判

### 异步 I/O

feeds（RSS/JSON Feed）、sitemap.xml、robots.txt 的生成与页面渲染无文件冲突——写不同路径。`std::async` 在渲染启动时并行执行 I/O 任务：

```
串行：render_locales → feeds → sitemap → robots  (~0.9s)
异步：render_locales (0.6s) ∥ feeds+sitemap+robots (0.3s)  (~0.6s)
```

省 ~0.3s。

### JS 模块导入指纹

ES 模块的 `import` 语句不带 `?v=` 缓存破坏参数，浏览器按 URL 缓存模块。新增 `fingerprint_js_imports` 在构建期扫描所有 JS 文件，给 `import`/`export ... from` 语句追加 `?v=hash`。配合 Service Worker 缓存版本升级（`cdocs-v2` → `cdocs-v3`）彻底消除浏览器模块缓存过期问题。

### 静态资源路径注入

子目录页的 JS 动态加载 `assets/deps/mermaid.min.js` 等第三方库时，相对路径会解错。改为 C++ 构建期注入 `window.__cdocs_asset_root`（基于 `relBase` 计算）到 Scripts 组件模板，JS 只需 `window.__cdocs_asset_root + 'deps/xxx.js'`。

## 最终性能

| 场景 | 耗时 |
|------|------|
| 首次完整构建（含资产）| ~1.4s |
| 全量渲染（资产缓存）| ~1.2s |
| 增量构建（无改动）| ~0.85s |
| 增量构建（改 1 篇 .md）| ~0.9s |

对标：Hugo ~0.1s（Go 模板编译+全内存）、VitePress ~1.5s（500 页）、Docusaurus ~3s。Cdocs 作为 12MB 单文件零依赖 C++ 生成器，性能已达实用级天花板。

## 架构决策

以下优化方向经过评估后搁置：

- **模板预编译 AST**（Hugo 同款）：200+ 行改动，收益 ~0.2s，当前增量 0.85s 已足够实用
- **Nav 骨架缓存**：已实现但引入死链误报（skeleton/patch 重组逻辑与原始 `nav_groups_json` 不等价），暂移除
- **全局快检跳过**：无变化时 0.01s 退出已编码，需单独 debug
- **持久插件进程**：已就位但收益在当前 3 插件并行场景下为零（import 开销 ≈ 冷启动）

## Bug 修复：Service Worker 缓存污染

详见 [Bug：Service Worker 缓存污染](2026-08-04-sw-bug)。排查过程中发现的三个关键修复：

1. ES Module `import` 无缓存破坏 → 构建期追加 `?v=` 指纹
2. JS 动态加载静态资源路径不可靠 → C++ 注入 `window.__cdocs_asset_root`
3. Service Worker 生命周期不自动激活新版本 → bump 缓存版本号
