title: "Bug: Service Worker Cache Poisoning Causes Stale JS Module Imports"
date: "2026-08-04"
tags: ["bug"]
---

## Symptom

`mermaid.min.js`, `katex.min.js`, `katex.min.css` returned 404 on subdirectory pages like `tests/test-mermaid.html`, despite files existing on disk.

## Investigation

### 1. Path Resolution

The JS dynamically loads assets using relative paths. On subdirectory pages, `loadScriptOnce('assets/deps/mermaid.min.js')` resolves to `tests/assets/deps/mermaid.min.js` — wrong.

**Fix**: C++ build injects `window.__cdocs_asset_root` into the page via the Scripts component:

```html
<script>window.__cdocs_asset_root="../assets/"</script>
```

`util.js` reads this: `(window.__cdocs_asset_root || 'assets/') + 'deps/mermaid.min.js'`.

### 2. Root Cause: Service Worker

After the path fix, 404 persisted. Incognito mode worked — pointing to the Service Worker.

The old SW (`cdocs-v2`) cached the old `util.js`. SW lifecycle means new versions only activate after all tabs are closed.

**Fix**: Bumped cache version `cdocs-v2` → `cdocs-v3`.

### 3. Chain Discoveries

- **ES module imports lack cache busting**: `import` statements don't carry `?v=` fingerprints. Added `fingerprint_js_imports` in C++ build to append `?v=hash` to all `import`/`export ... from` statements.
- **SW registration path**: `pwa.js` registered `./sw.js` — breaks on subdirectory pages. Fixed to derive from manifest link.

## Lessons

1. ES module `import` URLs have no automatic cache busting — must add `?v=` at build time.
2. Service Worker cache is independent of browser HTTP cache and doesn't hot-update.
3. C++ build-time injection is more reliable than DOM/`import.meta`-based path resolution in JS modules.
